# P4 — Constrained solver

**Days 5–7. Still no LLM.**

## Goal
Close the many-to-one mapping problem algorithmically. Keeping this tier deterministic is itself the signal — it shows you know where AI does and doesn't earn its cost.

## Build
`src/milaan/match/solver.py`
- Candidate windowing: `[date − 1, date + 3]` from `config/policy.yaml`, bucketed by `settlement_id`
- Subset-sum against the bank credit, tolerance `rounding_tolerance(n_rows)`
- Bounded search: cap subset cardinality, meet-in-the-middle or DP, hard per-cluster time-box. An uncapped subset-sum over 400 candidates will hang.
- **Ambiguity detection**: if two or more subsets satisfy the target, resolve nothing and mark for T3. This single rule prevents a whole category of false matches.
- Reverse direction: settlement rows with no bank credit; ledger orders with no settlement (D10)

## Exit gate
1. Auto-resolve **+10 to +15 points** above the P3 baseline
2. **False-match rate did not rise.** If it did, tolerance is too loose or ambiguity detection isn't firing — fix before proceeding.
3. Zero hangs across all three batches, with the time-box logged when it triggers
4. Per-class table shows D01, D02, D07 largely resolved here

## Expect to fail here first
Combinatorial explosion and confident-wrong-subsets both live in this phase. Both are excellent `what broke` material — write them up in `DECISIONS.md` with the metric before and after.

## If behind
Cap subset size at 3, accept lower recall on large batches, record the limitation.
