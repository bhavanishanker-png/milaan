# P1 — Synthetic data engine

**Days 1 (pm) – 2. This is half the project.**

The quality of your evaluation is capped by the quality of your generator. A generator that only produces clean matches yields a 99% match rate that means nothing and dies to the first panel question.

## Build
`src/milaan/generate/`
- `entities.py` — orders → payments → settlement batches → bank credits, with correct fee/GST/net arithmetic via `normalize.fees`
- `discrepancies.py` — **one function per D-code**, D01–D15 (see `docs/SPEC.md` §4). Each returns the label record it injected.
- `narration.py` — the six bank narration templates: full UTR, RTGS format, IMPS format, UTR absent, UTR truncated, non-settlement UPI credit
- `noise.py` — rent debits, GST payments, inter-account sweeps, direct customer NEFTs
- `labels.py` — writes `labels.json` (**the only file in `src/` allowed to touch labels**)
- `cli.py` — `python -m milaan.generate.cli --batch a --seed N --records 1000 --out data/a`

## Requirements
- Injection rate ~15% of records
- All 15 D-codes present in every batch, counts printed on generation
- 2–3 **deliberately unresolvable** cases per batch — a credit with no supporting data anywhere. A system claiming 100% resolution is lying, and these prove the escalation path works.
- Bank credits are **aggregated**: one credit = one settlement batch of many payments
- Fully seeded — no unseeded `random`, no `datetime.now()`

## Exit gate
1. Same seed → byte-identical output, twice
2. All 15 codes present, counts printed
3. **Hand-trace three injected discrepancies through the raw CSVs yourself.** If you can't trace them by hand, your labels are wrong and every metric downstream is fiction.
4. Batch C generated, then not opened again until P8
